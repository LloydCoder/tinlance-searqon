# Release and Artifact Provenance

Searqon releases are created from reviewed, versioned source tags. The published-release workflow is intentionally separate from pull-request CI.

## Release procedure

1. Confirm the release candidate is merged to `main` and CI, CodeQL, and secret scanning are green.
2. Update `package.json` and `package-lock.json` versions together.
3. Run the complete test suite and `npm audit --audit-level=high`.
4. Create a GitHub Release with a tag matching the package version exactly (for example, `v0.2.0`).
5. Publish the release. The workflow verifies the tag/version match, runs tests and dependency audit again, creates the npm tarball, generates a CycloneDX SBOM, and computes SHA-256 checksums.
6. The workflow attaches the package, SBOM, and `SHA256SUMS` to the GitHub Release and creates a Sigstore-backed GitHub artifact attestation for the package and SBOM.

## Verification

Use GitHub CLI to verify the package attestation against the expected repository and workflow identity:

```bash
gh attestation verify searqon-0.2.0.tgz -R LloydCoder/tinlance-searqon
```

Verify the downloaded artifact checksums:

```bash
sha256sum --check SHA256SUMS
```

The SBOM is generated from the locked npm dependency graph. It is a build-time inventory, not a guarantee that every transitive dependency is free of vulnerabilities. Review Dependabot and npm audit findings before release.

## Scope and limitations

- The workflow publishes release assets to GitHub Releases; it does not publish to the npm registry.
- The attestation is generated by GitHub Actions using OIDC and Sigstore. It is not a developer's personal code-signing signature.
- A published artifact must be verified against the expected repository and workflow identity before use.
- Branch protection and required status checks remain a repository-administration control and must be verified separately.
